# 锚点式出处检查：事实件逐字必查，叙述散文放行

## 背景

#119（2026-07-10）把主张检查收紧为"每个分句的全部有效词按顺序出现在被引证据里"
（`validateSingleClaimSupport` 尾部的 `hasOrderedLexicalSupport` 硬门）。实测后果：

- 真实剪藏文章（X 长文）过导入流水线，中文卡每张 18-29 条 error，英文卡 18-22 条，零幸存
  （5 轮实验，见 `docs/specs/2026-08-03-paste-article-text.md` 实验记录）。
- 全库口径：收紧后 source_import 成功出卡的模型运行仅 1 次（收紧当天凌晨）；
  此后三周半新增卡片全部来自 followup_generation——其证据是产品自己生成的中文卡，
  原文引原文才通得过词序检查。外部文章进口实际中断。
- 根因是体裁矛盾：卡片设计（hook、比喻、场景化 thread）天然是转述，
  逐字词序检查只接受近摘抄体。中英文皆死，非翻译问题。

用户拍板（2026-08-03）：改锚点式——**数字、技术名词、方向、否定这些"事实件"仍须逐字
（或规则化等价形式）在被引证据里找到；叙述性散文不再要求逐字词序。**
明示接受的代价：避开所有锚点的空话、以及"真实体 + 编造谓词"（如"X 已被弃用"）可能溜过。
检查仍是确定性规则，不引模型、不建同义词表。

## 现状机制（改动落点）

`packages/core/src/harness/groundingGate.ts`：

- 证据 = 引文的 quote 文本（`collectClaimEvidenceTexts` :388-396），quote 本身另有验真（#141）。
- `validateClaimSupport` :500 把主张切分句，逐句进 `validateSingleClaimSupport` :559。
- 单句检查顺序：无证据→拒；beyond-source 标记→放；**数字**（:596-605，只对
  最佳重叠句 `localEvidence`）；**方向**（:607-618）；**否定**（:620-642）；
  **专名**（:644-657，对全部证据）；逐字子串→放（:659-668）；
  **词序硬门（:673-682，本次要拆的）**。

## 改法

### 1. 词序硬门变成选项，卡片路径换锚点核对（同文件，`validateSingleClaimSupport` 尾部）

**（实现时修订）** 原计划直接删掉词序硬门；实测发现 `validateClaimSupport` 是共享原语，
深读段落门禁、概念简报、有据问答三个面也在用——它们的体裁是近摘抄（或有确定性兜底），
无模型时词序门是它们唯一的幻觉防线，不该被捎带放松。改为：

- `ClaimSupportOptions` 新增 `supportMode: "ordered" | "anchors"`，**默认 "ordered"（原语义原样保留）**；
  只有卡片门禁（`getClaimSupportOptions` 的全部四个分支）显式传 `"anchors"`。
  深读、概念简报、问答不传 → 行为一字不变。
- 锚点模式下的核对 `findUnsupportedClaimAnchors(claim, evidence)`：
  - **含中日韩文字的分句**：句中所有拉丁字母词（长度 ≥2）都是锚点——
    中文叙述里夹的 `KV cache`、`token`、`transformer` 全须在证据里找到
    （沿用 #149 的词形容忍：单复数、连字符/空格/下划线互换、大小写；不做语义）。
    连接词缩写（vs/etc/eg/ie/aka）排除——真实库里 "GQA vs MQA" 的 `vs` 是散文胶水，
    不是技术名词。
  - **纯拉丁文分句**：带符号的技术记号（`C#`、`A/B`、`TCP/IP`、`ELU+1`）永远是锚点
    （专名扫描分不清 `C#` 和 `C`）；其余沿用现有专名判定，`checkProperNouns` 已开时
    不重复查第二遍。
  - 有锚点且全部找到 → 通过；零锚点（纯叙述胶水）→ 通过；任一锚点找不到 → 拒，
    理由写明是哪个锚点。
- **（实现时修订，端到端复验后再修订）数字检查按语种分流**：
  先按"维持分句局部"实现（smoke 里"从邻句借数字"的整套保护依赖分句局部性），
  端到端复验发现这在跨语种下是错的——中文分句和英文证据没有词面可对齐，
  最佳分句选得近乎随机："其中 2 个共享处理所有 token" 对上的是
  "process every token"，而不是同一句里含 "Two are shared" 的那半句。
  最终形态：**同语种保持分句局部（借数字的旧防线原样有效），
  跨语种放宽到整条引文**。代价明示：跨语言卡可以在同一条引文里把数字
  安到错误的主语上；编造原文没有的数字仍被拦（实测拦住了模型自己算出的
  "18 个专家" = 2 + 16）。
- 方向、否定、数字、专名、逐字子串快路、beyond-source、无证据即拒：**全部原样保留**。
- 顺手修掉三个既有的洞/噪音（两种模式共享，端到端复验时暴露）：
  - 专名匹配从裸子串换成 #149 词边界匹配（原来 `RAG` 能在 `storage` 里"找到"）；
  - 分句时短记号括号粘回宿主：纯数字（`GPT-2 (2019)`）和无空格短记号（`O(N²)`）
    都不再被拆成孤立分句——大 O 记号原来会被撕出一个孤字母 `O`；
    带空格的措辞括号照旧拆分，事实性补语仍须自证；
  - 单个大写字母不再当专名候选（`O(N)` 的 `O` 是数学记号碎片，不是实体，
    真实跑批里制造了 6/34 条噪音）。

### 2. 专名判定的一处修正（`findUnsupportedProperNouns`）

句首的普通大小写单词（`[A-Z][a-z]+` 且非驼峰/全大写/连字符/多词专名）不再当专名——
英文每句开头必大写，"Scaling brings a trade-off" 的 "Scaling" 不是实体。
词序硬门拆掉后这是英文叙述句最大的误杀源。
代价（写进注释）：编造的单词实体恰好出现在句首且句中不再复现时会漏过。

**（实现时修订）降级只认构词后缀** `ing|ed|tion|sion|ment|ness|ity|able|ible|ly`：
裸 `s/es`、`er`、`al` 从后缀表剔除——Mars、Postgres、Sutskever、Mistral 这些名字
恰好长这样，句首出现时不能被降级放行（宁可错杀句首复数名词开头，不放过编造的名字）。

### 3. 数字单位的中英等价（`extractNumericTokens`）

现规则把 "22,580 倍" 归一成 `22580倍`，而英文证据 "a factor of 22,580" 归一成 `22580`，
永远对不上。补规则化等价（双侧同样归一，保持对称）：

- 倍数标记互认：`倍` / `times` / `x`（紧贴数字）/ `×` / `-fold` → 统一成 `×`；
  前置形式 `(a) factor of N` → `N×`。
- 年份：`N 年`/`N years` 当 N 是 19xx/20xx 四位年份时剥掉单位（"2019 年" ↔ "(2019)"）。
- 技术记号保护：`ELU+1`、`Top-2` 这类"字母+数字"记号先打码再提数字，
  不再把 `+1` 当独立数字主张（其字母部分仍受专名/锚点约束）。
- ~~**不做**：英文单词数字（seven ↔ 7）不解析，missing 仍拒。~~
  **（2026-08-03 用户推翻）**：单个单词的英文基数词（two…twenty、thirty…ninety、zero）
  与阿拉伯数字互认（"Two are shared" ↔ "2 个共享"）。`one` 仍除外——它作代词/冠词
  （"one of the ways"）会把普通散文错认成数字主张。多词数字（twenty-two thousand）仍不解析。
- **（2026-08-03 用户拍板，实验第七轮暴露）**："增加/提升"在中文里常指"添加组件"而非数量上升；
  证据里写 add/introduce/加入/新增/添加/引入 即可支撑"增加"形状的主张。
  只放宽证据侧：英文卡自己写 "adds" 不因此触发方向检查。

### 3b.（端到端复验时新增）四处与语种、体裁、引文范围有关的修正

前三条是复验暴露的确定性误杀，第四条是复验暴露的老 bug：

- **否定跨语种同因**：负向表述常落在相邻分句（"…avoids that redundant work"），
  按最佳分句判极性会把忠实转述判成反转。跨语种改为对整条引文判——
  引文里完全没有负向表述，才拒绝一条否定式主张；同语种维持原样。
  另把 add/prevent 一类的"回避动词"（avoid/prevent/eliminate/避免/无需/免去/省去）
  认作负向表述，两侧同样处理。明示代价：跨语言下"在本来就带否定的证据里做反转"不再被拦。
- **假设句不比对极性**：`如果/若/假如/倘若/万一/要是/假设/设想`（英文 if/suppose/imagine）
  开头的分句是出题人的假设，不是来源的断言；其中的实体、数字、术语照查。
- **所有格漏匹配**：原文只写 `Schlag’s paper` 时，词切分把 `schlag’s` 当一个词，
  `Schlag` 匹配不上。两侧同样剥掉 `’s/'s`（概念判定共用同一个匹配器，一并受益）。
- **块级引文从未当过证据**（老 bug，非本单引入）：`validateGrounding` 给每条主张
  传的都是卡级 `post.citations`，thread 块自己的引文只做了 quote 验真就丢掉了。
  后果是"块正确引了点名该实体的那一段"仍判不通过。改为**卡级 ∪ 块级**：
  卡级引文承载卡的共同主语，块级引文承载这一块新增的内容。
  （不改成"只用块级"：那样每个块都得把卡的主角名字重引一遍。）
  复习题和图谱边没有自己的引文，仍只吃卡级——已写进提示词。

### 3c.（用户拍板 2026-08-04）测验选项与假设句：豁免方向/否定比对，保持纯程序规则

用户裁决：门禁继续用确定性规则，**不引入模型判断**（模型复核层——只对被拦的
方向/否定类失败复核翻案、数字与专名不许翻——作为后手记录在案，未立单）。
本次落两条体裁规则，都只免方向和否定的比对，实体、数字、拉丁术语照查：

- **选择题选项**：问题类主张（quiz 正文、块内提问、复习题）里以选项标记开头的
  分句（`A.`–`E.`，标记后须接空白或中文，防 "E.g." 误判）不当断言——测验按设计
  要写错误选项（"A. 增加容量；B. 减少容量"），把选项当断言必拦其中一个方向。
  答案与解析分句照旧全查。分句器会把 "A." 从选项正文上切开，所以在
  `validateClaimSupport` 的分句循环里按"分句在原文中的前缀"识别，
  不动共享的分句器。
- **假设句作用域修成整句**：3b 只放过以如果/若/假如开头的分句，
  "如果…，但发现内存不够" 的后半句照拦。现在假设标记生效到句号为止，
  下一句恢复照查；方向检查同步纳入假设豁免（3b 只免了否定）。
  明示代价：卡片给事实句套上"如果"前缀可以躲开方向/否定比对（数字专名仍拦）。

### 4. 概念字段（`$.concepts[]`）不动

#149 的规则原样保留。但生成提示词补一句硬约束：概念必须是**原文中逐字出现的词组**
（`contentLanguage.ts` 概念指引处）。实验里概念仍是第二大卡死源，先用提示词治，
不动门禁；若实测仍高频误杀，另立单。

## 不做

- 不引模型、不建同义词表、不做语义相似度。
- 不改 severity 映射（failed → error 仍整卡拒收）、不改 `sameSourceFollowup` 语义。
- 不改引文验真（假 quote 仍拒收，#141）。
- 不改 `$.concepts[]` 判定分支。
- 不动 `apps/web`、`apps/api`。
- 词数字（seven→7）不做。
