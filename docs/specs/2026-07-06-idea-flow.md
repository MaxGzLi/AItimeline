# 想法流:发想法 → 库内关联 + 追问 + 正反取证

## 背景与问题

用户的输入不都是问题,有时是一个假设/原创想法——定义上外部可能根本没有现成来源。现在这类输入要么被当问题拒答(dark),要么当普通笔记只得到一条礼貌回帖。设计共识:**grounding 红线约束的是断言,不是提问**——观察员不能凭模型记忆评判想法,但可以引用库内已有卡、可以追问、可以提议去找支持与反驳两边的证据。

依赖:spec ①(提问闭环)已合并——复用其多轮上下文、确认 action 机制、research 管线与通知流。

## 设计

### 1. 入口:发布框加「想法」标签(web)

- 发布框(问你的知识库那个输入框)加一个 chip 开关:默认「问题」,可切「想法」;不做自动识别(分类错了伤信任)。
- 「想法」提交走 `POST /api/notes`,body 加 `kind: "idea"`(现有 note 路径扩展,老调用不带 kind 时行为不变)。

### 2. 想法回帖三件套(core + api)

想法入库后,观察员回帖依次包含:

1. **库内关联**:从想法文本提概念(过 spec ② 的 resolveConcept 归一),取重合度最高的 ≤3 张已有卡,引用出处摆出来——「你库里这几张和这个想法有关」。库里空白就直说「库内没有相关材料」。
2. **追问 ≤2 个**(复用 spec ① 的确认 action 机制,kind `idea_probe`):目的是把想法收敛成可检验的形状。模型路径生成针对性问题;确定性回退用固定模板:「这个想法里,哪部分你觉得是可以被验证的?」「它和你库里《X》的说法一致还是冲突?」用户的回答作为新一轮(带 previousTurns)追加进线程。
3. **可检验子问题**:把想法拆成 ≤3 个可搜证的子问题(模型生成;确定性回退:用想法原句+概念组合),每个带「找证据」按钮。

### 3. 正反取证(api,复用 research 管线)

- 点「找证据」触发 `research_question` job 的变体 `research_idea`:**两组 queries**——支持向(`X evidence/case`)与反驳向(`X criticism/limitations/counterexample`),各搜各导(每边 top 2)。
- 结果回帖**分正反两栏**:「支持的证据」「相反的声音」,各自引用导入的卡与出处;一边空了如实写「没找到这一侧的靠谱来源」。结果走 spec ① 的通知流。

### 4. 想法进图谱(core)

- 想法本身成为图谱节点(新 node 来源 kind `idea`,视觉沿用 ghost 样式但可区分,比如虚线描边);
- 取证导入的卡通过概念边自然挂上来;追问答复(用户断言)不生成知识卡、不进复习——想法节点的「证据度」只由真实导入的来源撑起。

## 明确不做

- 不评价想法对错;观察员的每个断言必须有引文,评价性语言(「这个想法很好」)一律不出现。
- 不做想法专属视图/孵化器页面;一切在回帖线程与图谱里发生。
- 不做自动识别问题 vs 想法。
- 用户在追问里的回答不进复习、不生成卡。

## 验证标准

1. `npm run typecheck` / `npm run build` / `npm test` 全绿。
2. smoke-api 扩展断言(硬要求,离线):kind:"idea" 的 note 产生三件套回帖(库内关联引用真实卡、追问 action、子问题 action);research_idea 双向 queries 且分栏结果落通知;库内无关联时文案如实;旧 note 调用(无 kind)行为不变。
3. smoke-core:想法节点入图谱、样式 kind 正确;概念归一路径被复用。
4. UI 截图:想法 chip、三件套回帖、正反两栏结果、图谱里的想法节点。i18n zh/en 成对。
