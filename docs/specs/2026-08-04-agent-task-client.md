## 「任务」的统一模型

一条任务 = agent 做的一件事。列表合并三个来源,**不改数据结构**:

| 来源 | 存在哪 | 现状 |
| --- | --- | --- |
| agent 自发的策展任务 | `curation-jobs.json` 的 records | 588 条,10 种 kind |
| 用户派的活 | 同上(照 `preferences.mjs:78-107` 手工拼任务) | 已跑通一次 |
| 用户问的问题 | 快照 `agentTurns` | 8 条 |

## 会话流用现有字段拼

已核实(读的是 `apps/api/data/curation-jobs.json` 真实记录,不是推测):

| 流里的一步 | 字段 |
| --- | --- |
| 为什么派这个活 | `job.reason`(中文人话,例:「你说想搞懂「智能体的长期记忆」,观察员会去找这方面的来源。」) |
| 排队 / 计划运行 | `createdAt` / `job.runAfter` |
| 领取 | `claimedAt`(= `startedAt`),`workerId` |
| 检索到的候选 | `result.discoveredSourceCandidates[]`(带 title / url / relevanceScore,实测一次 8 条) |
| 完成 | `completedAt`,`result.message` |
| 产出的卡 | `result.sourceImport.posts[].id`(结算压缩后只剩 id,拿 id 回快照查全文) |
| 失败 | `status: failed` + `lastError`(例:`Source candidate could not be processed.`) |
| 重试次数 | `attempts` |

**不做**:更细粒度的中间步骤事件(模型在想什么、哪个 URL 抓超时)。要加得给快照新增集合,而 v2 快照缺集合会拒绝加载、必须连解码器一起改;现有五步已够 Codex 观感。留作后续。

**要做的一件小事**:`result.message` 现在是英文(`Imported source candidate into timeline-ready knowledge posts.`),界面上要给每种 kind 一句中文说法,按 kind 映射即可,不动数据。

## 顺带解决 #12(剪藏可靠性)

现在剪藏失败是无声的:任务变 `failed` 就沉底,用户不知道自己保存的东西死在哪,再保存同一条会因为任务 id 撞车被静默丢弃。本期解决一半——**失败在列表里可见、带原因、带重试按钮**;另一半(重试时给新 id,别撞老记录)是后端小改,一并做。

## 改动清单

### 后端(apps/api)

- 新增 `GET /api/agent/tasks`:瘦端点,合并队列记录 + agentTurns,按时间倒序,只返回列表所需字段(id / kind / 标题 / 状态 / 时间 / 产出数)。**不得让前端继续吃 19MB 的 `/api/snapshot`。**
- 新增 `GET /api/agent/tasks/:id`:详情,把上表那些字段整理成一条有序的步骤流 + 产出卡(按 post id 从快照取)。
- 新增 `POST /api/agent/tasks`:派活。走已跑通的两条路——能解析成学习意图的走 `preferences.mjs` 那条(写记忆 + 排 `discover_sources`);其余走 `runConversationTurn`(已在 `/api/agent/ask`)。回话如实,不夸大。
- 新增 `POST /api/agent/tasks/:id/retry`:失败任务重排,**用新 id**(照 `hashText(topicKey|now)` 的先例),避免撞老记录被静默丢弃。
- 端口:桌面版默认 **8787**(产品端口),被占退 **8788**。不用 8791——本机 8791 被一个长驻 python 占着(实测 pid 804)。

### 前端(apps/web)

- 新增 `src/views/TaskClientView.tsx`:左列表 + 右详情两栏,照 `TimelineView` 绕开共享 `<main>` 自己渲染整套栏目的先例(`App.tsx:2674` vs `:2780`)。
- `App.tsx`:`ViewKey` 加一项并设为默认首屏;左栏导航拆两段(任务客户端置顶,原八项收到下面一组次级入口)。`BaseView` 保留但从首屏退下(不删,避免连带回归)。
- 样式:新增独立前缀类名段,不改 `xshell.css` 现有规则;grid 由该视图自己覆盖。
- 对话历史:`agentTurns` 现在**不存回答正文**(`persistenceStore.ts:125-136` 只有 question/intent/tier/zone/status/threadId/answerCardId)。本期在任务详情里用 `answerCardId` 反查卡片展示答案,不新增会话集合;"刚才那个再讲细一点"这类指代本期不支持,写进已知限制。

### 前置坑(不修则第一句中文提问就被拒答)

`conversationAgent.ts:190` 用问题原文**字面匹配**概念名判断"库里有没有",而概念被钉死成英文。中文问 "MoE 是什么" 匹配不到 `Mixture-of-Experts`,直接掉进"库里没有,要不要我先去找来源"。快照里已有 `conceptAliases` 集合,本期接上它做匹配扩展(不改概念本体)。

### 卡顿(已不成立,2026-08-04 复测)

原以为 `POST /api/agent/preferences` 要 ~17 秒(一次把 19MB 快照整写三遍,`App.tsx:2369` 注释)。**#162 的快照读路径缓存已经把它解决了**:拿真数据(19MB 快照 / 596 条队列记录)复测,调喜好那条 1.30 秒、提问那条 1.58 秒,任务列表 0.30 秒。不用再去合并写入。

真正剩下的延迟在别处:frontier 分区的提问会同步等一次真实网络搜索,见下面的待定策略。

## 待定策略:frontier 提问会静默真发搜索

概念匹配修好之后,中文提问从 dark 挪进了 frontier,而这两个区对「要不要去搜来源」的处理是反的。`handleAgentAsk` 只在这一轮带 `confirm_discovery` 动作时才不搜:

| 分区 | 动作 | 会不会真搜 |
| --- | --- | --- |
| dark | `confirm_discovery, discover_sources` | 不搜(有确认门) |
| frontier | `start_series, discover_sources` | **搜**(没有门) |
| learning | `continue_deeper, reframe_simpler` | 不搜(没有 discover 动作) |

搜索 key 配着的时候这条路是活的:问一句中文会花掉搜索额度、写候选源,回话还要等搜索回来。不是本期引入的(英文提问一直如此),但门设反了——知道得少反而要确认。等用户定:frontier 的库内问答不自动搜(回话里本来就有「为这个问题找来源」按钮 + `research.mjs:725` 的按需端点),还是维持现状。

## 验收

- 双击桌面应用即开;插件剪藏后,任务列表里立刻出现一条"导入剪藏来源"的任务,能看到它排队→领取→产出卡的全过程。
- 派一句活("帮我找找关于 X 的来源"),列表出现新任务,跑完能看见产出的卡和逐字引文出处。
- 中文提问不被误判为库外;答不出时如实说"库内暂无足够依据",不编。
- 失败任务显示原因,点重试能重新跑(不撞老记录)。
- 八个旧视图从次级入口进去功能不变。
- 无模型配置时全链路仍可用(确定性回退)。
- 单测:任务列表合并与排序、步骤流拼装、重试 id 生成;smoke:派活 → 任务出现 → 详情可读。
