# 粘正文成卡

## 背景

现在产出真正知识卡（多张、带引文、过出处检查）的唯一入口是"给网址，服务器去抓"
（`/api/import/article` → `transformArticleUrl` → `fetchArticle`）。

登录墙后面的内容——用户明确提到的 X 文章——服务器抓回来是登录页，不是正文。

已有的"直接给文字"的两条路都是廉价版：`transformUserNote` 和 `transformConversationCapture`
都是**确定性套模板出一张卡**，不过模型、不过出处检查，对话采集还限 4000 字。不是这里要的东西。

本单是用户拍板的第一步：**先不做浏览器插件，先把"正文 → 知识卡"这段打通并验证它好不好使。**
浏览器端（书签工具或正式插件）等这段验证过再说。

## 目标

用户能把一篇文章的正文和它的网址交给产品，得到和"导入网址"完全同等质量的知识卡：
多张卡、每张挂引文、过出处检查、进信息流。

具体行为：

1. **新接口 `POST /api/import/text`**，收 `{ url, title?, text, createdAt?, recommendedBecause? }`。
   - `url` 必填：出处是产品承诺，卡片必须有可追的地址。
   - `title` 选填：不给就取正文第一行（截断），不去猜、不去抓。
   - `text` 必填：切成段落后一段都不剩就报错拒收（对齐 `fetchArticle`
     的 "Article did not contain enough readable text."）。
2. **切段落与抓网址走同一套规则**：沿用 `defaultMaxChunks` / `defaultMinParagraphLength`，
   按空行切，太短的段落丢掉，段数封顶。不新造一套参数。
3. **来源编号与网址导入一致**：都用 `buildArticleSourceId(url)`。
   于是"同一篇文章先抓过、后来又粘了一次正文"会被认成同一个来源——
   配合刚合并的 #151，同来源就是替换，不会变成两份。
4. **下游一行不改**：切完段落之后的一切（模型生成、引文、出处检查、发布计划）
   走的必须是和网址导入完全相同的那段代码，不允许复制一份。
5. **网页上能用**：`SourceImportPanel` 加一个"粘正文"模式，一个网址输入框 + 一个正文文本框。
   默认仍是网址模式。

## 不做

- **不做浏览器插件、不做书签工具**（用户已明确本轮先不做）。
- **不做配图**：粘进来的正文没有首图，这批卡就是纯文字卡。不去按网址回抓图片。
- **不验证正文是否真的来自那个网址**：服务器无从核实，本地自用可接受。
  这是开源自托管前要处理的口子，记进「开放问题」，本单不挡路。
- 不改 `/api/import/article` 和 `/api/import/youtube` 的现有契约。
- 不改笔记 / 对话采集这两条既有的模板路径。
- 不改来源质量检查的判据（见开放问题）。
- 不改移动端 `apps/mobile`。

## 验收清单

      来源编号、正文存档内容、段落切分结果一致。断言加在
      `packages/core/src/transform/articleImport.test.ts`。
- [ ] 下游未被复制：`transformArticleUrl` 与 `transformArticleText` 调用的是同一个共用函数。
      **验证方式：把共用函数改坏一次，两条路的测试要同时变红。**
- [ ] 正文切完一段都不剩 → 抛错拒收，有断言。
- [ ] `title` 不给时取第一行；给了就用给的，有断言。

- [ ] `npm run typecheck`、`npm run build`、`npm test` 全绿。
- [ ] UI 截图：网址模式、正文模式、粘完提交后的结果，放

## 实验记录（2026-08-03，真实剪藏 + 真模型，共 5 轮，未写用户数据）

输入：用户 Obsidian 剪藏的 X 文章《22580: From GPT2 to Kimi3, Explained》（头部自带
source 网址/标题/作者，正文 108 块：91 段文字 + 17 段代码 + 22 张图链接）。
脚本：`scratchpad/paste-experiment/run.mjs`（worktree 会话临时目录）。

结论：

1. **剪藏格式天生适配**，frontmatter 直接提供 url/title/author/published；服务器抓 x.com
   只能拿到登录墙，插件/剪藏是唯一入口，方向确认。
2. **来源质量检查不是障碍**：5 轮全部 accept，分数 0.85（担心的"太短被拒"未发生）。
3. **致命阻塞——接地门禁**：中文卡（对英文证据）每张 18-29 条 error；英文卡（对英文证据）
   也是 18-22 条 error。#119（2026-07-10）后的门禁要求每个主张分句的词按序出现在被引证据里，
   等于只接受近摘抄体；卡片体裁（hook/比喻/场景化 thread）天然是转述，无解。
   **在门禁规则变更前，本功能做出来产出为零，暂缓实现。**
4. **全产品影响面（快照全口径核实）**：2026-07-10 门禁收紧后，source_import 成功出卡的
   模型运行仅 1 次（07-10T00:35，收紧边界）；此后所有新增卡片全部来自 followup_generation
   （6 次出卡），其证据是产品自己生成的中文卡（原文引原文，天然能过词序检查）。
   外部文章进口实际中断三周半。
5. 顺手发现的三个小障碍（实现时要处理）：
   - 长文截断：85 个合格段落只吃前 24 段（`defaultMaxChunks`），文章后半段从未进流水线；
   - 模型输出上限 `defaultMaxTokens = 8192` 会把长输出截成非法 JSON 整单报废（16384 实测可用）；
   - 模型超时写死 60s（`openaiCompatibleClient.ts:106`）不可配，英文轮两次撞死。
6. 代码块入 chunk 会稀释证据（模型全部引文集中在 3 个块），剔除后引用分布正常——
   实现时预处理应剔除代码块。

## 假设与开放问题

- **假设**（用户可推翻）：网址必填。理由是没有网址的卡追不到出处，与产品承诺冲突。
- **开放问题（要实测才知道）**：来源质量检查会不会把 X 上的短文章挡掉。
  真实日志里已经见过 "Body is too short to support a learning card." 这条拒收理由。
  本单**不动判据**，先做出来实测；真挡了再单独决定是放宽还是给个明确提示。
- **开放问题**：粘进来的卡没有配图，在刚上线的信息流配图改动之后会不会显得突兀。
  先看实际效果。
- **开放问题（开源前必须解决）**：服务器无法核实正文真的来自所声称的网址。
